## A. 60-second explanation

> "I built an enterprise data-management platform on **MySQL**. It takes operational data - customers, products,
> orders, order lines and payments - from CSV files that represent different source systems. A **Python and Pandas
> ETL pipeline** cleans and validates every row, loads the good rows into **staging tables**, checks references in
> SQL, and then upserts them into a **normalized 3NF schema** of 12 tables with primary keys, foreign keys, CHECK and
> UNIQUE constraints. Bad rows aren't lost: each problem is stored in a **data_quality_issues** table with a severity
> and a status, and every ETL run is logged with rows read, inserted, rejected and its status.
> In the database I used **views, stored procedures, functions, triggers and indexes** - for example triggers write an
> **audit log** of every change and keep order totals in sync, and a stored procedure records payments inside a
> **transaction**. A **FastAPI** backend exposes the data through about 20 REST endpoints, and a **React** dashboard
> shows business KPIs, ETL runs and data-quality issues."

## B. 2-minute explanation

> "The problem I wanted to solve is something every company has: data comes from several systems, it is messy, and
> people don't trust the reports. So the project has four parts.
>
> **First, the database.** MySQL with InnoDB. Twelve core tables: business tables - departments, employees, customers,
> products, orders, order_items, payments - plus ETL metadata - data_sources, etl_jobs, etl_execution_logs - and
> monitoring - data_quality_issues and audit_logs. It's normalized to 3NF: for example order lines are a separate
> table, which resolves the many-to-many between orders and products. I protect the data with constraints - CHECK
> constraints on statuses and amounts, UNIQUE on business keys like email and transaction reference, and foreign keys
> with different ON DELETE rules.
>
> **Second, the ETL.** Python reads the CSV as text, cleans formatting - like lower-casing emails or standardising
> segment names - and validates each row: required fields, email format, real dates, no negative amounts, allowed
> values, and duplicates. Valid rows go to staging tables; then SQL resolves business keys like `CUST-1001` to
> database ids, rejects rows whose customer or product doesn't exist, and upserts into production with
> `INSERT ... ON DUPLICATE KEY UPDATE`, so re-running is safe. Each job is one transaction. In the demo load, 1,509
> order rows were read, 1,495 loaded and 14 rejected - five of them because the customer didn't exist, and that
> cascaded: their order lines and payments were rejected too.
>
> **Third, database logic.** Triggers write an audit trail with old and new values as JSON and keep the order total
> equal to the sum of its lines. Stored procedures enforce rules - like allowed order status transitions - and
> `sp_record_payment` locks the order row, checks the balance and commits or rolls back. Another procedure runs
> cross-table checks like 'delivered but not paid' and found 25 such orders.
>
> **Fourth, API and dashboard.** FastAPI with SQLAlchemy and Pydantic, split into routes, services, models and schemas.
> The React dashboard shows revenue trends, ETL runs, open data-quality issues by severity, and the audit log.
> I tested it with 43 automated tests: constraints, triggers, procedures, transactions, the API and the ETL rules."

## C. Architecture

```
CSV sources → [Python ETL: extract → clean → validate] → staging tables → [SQL checks + upsert] → production tables
                         ↓ bad rows                                   ↓ bad references            ↓ triggers
                  data_quality_issues  ←───────────────────────────────┘                        audit_logs
production tables + views + procedures ←→ FastAPI (routes → services → SQLAlchemy) ←→ React (Axios, Recharts)
```
- **Why this split?** Each layer does what it is best at: Python for file handling and row validation, SQL for
  set-based checks against existing data, the database for rules that must hold for *every* writer, the API for
  access, React for presentation.
- Details: `docs/ARCHITECTURE.md`.

## D. Database explanation

- 12 core tables + 5 staging tables + 6 views + 3 functions + 5 procedures + 19 triggers + 15 secondary indexes.
- **Business:** departments, employees (self-referencing manager), customers, products, orders, order_items, payments.
- **ETL metadata:** data_sources (CRM, product catalog, order system, payment gateway, production DB),
  etl_jobs (a job *definition*), etl_execution_logs (one row per *run*).
- **Monitoring:** data_quality_issues, audit_logs.
- Surrogate integer PKs for joins + UNIQUE business keys from the source systems (`customer_code`, `sku`,
  `order_number`, `payment_reference`).
- Money in `DECIMAL(12,2)`, never FLOAT.

## E. Why MySQL?

- Mature, open-source relational database; very widely used in industry, so the skills transfer.
- **InnoDB** gives ACID transactions, row-level locking and enforced foreign keys.
- MySQL 8 added what modern analytics needs: **CTEs, window functions, CHECK constraints, JSON, invisible indexes,
  EXPLAIN ANALYZE** - all used in this project.
- Stored procedures, functions and triggers let me put critical rules inside the database.

## F. Why a relational database instead of MongoDB?

- The data is naturally **relational**: customers → orders → lines → products, orders → payments.
  Those relationships must be **guaranteed** (no payment for a non-existent order) - foreign keys do that for free.
- Money needs **multi-row ACID transactions** and strong consistency.
- Reporting needs **JOINs and aggregations** across entities - SQL is built for it.
- MongoDB fits flexible, document-shaped data (e.g. product catalogs with very different attributes, event logs).
  I actually used MySQL's **JSON column** for the audit log, where the shape varies per table - so the right tool
  per need, inside one database.

## G. Why normalization?

To store each fact **once**. That avoids:
- **Update anomaly** - a customer's email stored on 30 orders; change it in one place and the rest are wrong.
- **Insert anomaly** - can't store a product until someone orders it.
- **Delete anomaly** - deleting the last order loses the customer's details.
Normalization also makes constraints simple (one place to put UNIQUE on email).
Trade-off: more JOINs - solved with indexes and views.

## H. 1NF, 2NF, 3NF using THIS project

- **1NF** - atomic values, no repeating groups. An order with three products is **three rows** in `order_items`, not
  columns `product1, product2, product3` or a comma-separated list.
- **2NF** - (applies to composite keys) every non-key column depends on the **whole** key. In `order_items` the natural
  key is `(order_id, product_id)`. `product_name` would depend only on `product_id` → it lives in `products`.
  `quantity` and sale-time `unit_price` depend on both → they stay.
- **3NF** - no transitive dependency. If `employees` held `department_name`, it would depend on `department_id`, not
  directly on the employee → moved to `departments`. Orders don't store the customer's city for the same reason.
- **Deliberate exceptions:** `orders.order_total` (kept in sync by triggers) and `order_items.line_total`
  (a generated column). They are derived values the database maintains itself - controlled denormalization for
  reporting speed.
- **Why `order_items.unit_price` is not duplication:** it's the price *at the time of sale*. In my incremental batch I
  re-price five products; old orders must keep their old price.

## I. Primary and foreign keys

- **Primary key:** uniquely identifies a row; NOT NULL + UNIQUE; one per table. In InnoDB it is also the
  **clustered index** (rows are physically stored in PK order). Example: `orders.order_id`.
- **Foreign key:** a column that must match a PK in another table - **referential integrity**.
  `orders.customer_id → customers.customer_id`: you cannot create an order for a non-existent customer
  (MySQL error 1452 - one of my tests checks this).
- **ON DELETE options I used:** RESTRICT (customer with orders can't be deleted), CASCADE (deleting an order
  deletes its lines), SET NULL (if an employee is removed, their orders remain with `employee_id` NULL).
- **Surrogate vs natural key:** `customer_id` (surrogate, internal) vs `customer_code` (natural/business key, UNIQUE).

## J. What are indexes?

A separate sorted structure - a **B+tree** - on one or more columns that lets MySQL find rows without scanning the
whole table, like a book index. Cost: extra storage and slower INSERT/UPDATE/DELETE because indexes must be updated.

## K. Why did you create these indexes?

Each one comes from a real query pattern:
- `orders(order_date)` - monthly reports and date filters. EXPLAIN shows an *index range scan*.
- `orders(customer_id, order_date)` - "customer's orders, newest first". EXPLAIN ANALYZE: **38 rows read via the
  index vs 1,525 rows + a sort** when I made the index invisible, ~4× faster even on this small table.
- `orders(status, order_date)` - status alone has only 5 values, so I paired it with the date.
- `payments(order_id, status)` - "how much is paid for this order"; it's a **covering index** for counts.
- Monitoring indexes: `etl_execution_logs(job_id, started_at)`, `data_quality_issues(resolution_status, severity)`,
  `audit_logs(table_name, record_id, changed_at)`.
- **Not indexed on purpose:** boolean `is_active` (low selectivity) and staging tables (write-heavy, read once).
- Interesting finding: when I created `(customer_id, order_date)`, MySQL **dropped the index it had auto-created for
  the customer_id foreign key**, because the composite index already starts with that column.

## L. What are transactions?

A group of SQL statements treated as **one unit**: either all succeed (`COMMIT`) or none do (`ROLLBACK`).
In my project:
- `sp_record_payment`: `START TRANSACTION` → `SELECT ... FOR UPDATE` locks the order row → validate (exists,
  not cancelled, amount > 0, not more than the balance) → insert → `COMMIT`. An `EXIT HANDLER` does `ROLLBACK` on any
  error, e.g. "Payment exceeds outstanding balance" or a duplicate transaction reference.
- Each ETL job's load step is one transaction: issues, staging, checks, upsert and the log update commit together.

## M. ACID

- **Atomicity** - all or nothing. A failed payment leaves no half-inserted row.
- **Consistency** - every transaction moves the DB from one valid state to another; constraints (CHECK, FK, UNIQUE)
  are never violated.
- **Isolation** - concurrent transactions don't see each other's uncommitted work. InnoDB's default is
  **REPEATABLE READ**; I also used an explicit row lock (`FOR UPDATE`) so two payments for one order can't both pass
  the balance check.
- **Durability** - once committed, data survives a crash (InnoDB redo log).

## N. What is a JOIN?

Combining rows from two or more tables using a related column, e.g.
`orders JOIN customers ON customers.customer_id = orders.customer_id`. Normalization splits data; JOINs put it back
together for reading.

## O. INNER JOIN vs LEFT JOIN

- **INNER JOIN** returns only rows that match on both sides.
- **LEFT JOIN** returns **all** rows from the left table, with NULLs where there's no match.
- Example: "customers who never ordered" = `customers LEFT JOIN orders ... WHERE orders.order_id IS NULL`
  → 19 customers.
- Trap I handle in Q12: putting a condition on the right table in WHERE turns a LEFT JOIN into an INNER JOIN - so I put
  `o.status <> 'CANCELLED'` inside the `ON`.

## P. WHERE vs HAVING

- `WHERE` filters **rows before** grouping - can't use aggregates.
- `HAVING` filters **groups after** GROUP BY - can use `COUNT`, `SUM`...
- `SELECT customer_id, COUNT(*) FROM orders WHERE status <> 'CANCELLED' GROUP BY customer_id HAVING COUNT(*) > 15`.

## Q. GROUP BY

Collapses rows with the same values into one row per group so aggregates are computed per group - e.g. revenue per
month, orders per status. Every selected column must be grouped or aggregated (`ONLY_FULL_GROUP_BY`).

## R. Subquery vs CTE

- A **subquery** is a query nested inside another (in WHERE, FROM or SELECT).
- A **CTE** (`WITH name AS (...)`) names that subquery up front.
- CTEs are more readable for multi-step logic, can be referenced several times, and can be **recursive** - I used a
  recursive CTE for the employee reporting chain. Performance is usually similar; the optimizer often merges both.

## S. What is a window function?

A calculation across a set of related rows that **keeps every row** (unlike GROUP BY).
`FUNC() OVER (PARTITION BY ... ORDER BY ...)`. I used:
`ROW_NUMBER` (latest order per customer, latest run per ETL job), `RANK`/`DENSE_RANK` (top products per category,
top customers), `SUM() OVER` (running revenue), `LAG` (month-over-month growth), `NTILE(4)` (spending quartiles),
and `SUM(SUM(revenue)) OVER ()` for each category's share of total.

## T. What is a stored procedure?

A named, pre-compiled SQL program stored in the database and executed with `CALL`. It can take IN/OUT parameters,
use variables and IF, raise errors with `SIGNAL`, and control transactions. Benefits: business rules live in one
place for every client, fewer network round trips, permissions can be granted on the procedure rather than tables.
Mine: `sp_record_payment`, `sp_update_order_status`, `sp_get_customer_summary`, `sp_sales_report`,
`sp_run_data_quality_checks`. (These are MySQL stored programs - not PL/SQL, which is Oracle's language.)

**Procedure vs function:** a function returns one value and is used inside SELECT (`fn_order_balance(order_id)`);
a procedure is called on its own and can return result sets and manage transactions.

## U. What is a trigger?

SQL that runs **automatically** BEFORE or AFTER an INSERT, UPDATE or DELETE on a table, for each row, with access to
`OLD` and `NEW` values. Mine: cleaning/validation (BEFORE INSERT on customers), keeping `order_total` correct
(AFTER INSERT/UPDATE/DELETE on order_items), 12 audit triggers, and two that make `audit_logs` append-only.
Caution: triggers are "invisible" logic, so I keep them small and documented.

## V. What is ETL?

**Extract** data from sources, **Transform** it (clean, validate, standardise, map keys), **Load** it into the target.
(ELT = load raw first and transform inside the warehouse.)

## W. Why staging tables?

- A landing zone to **check a batch against production in SQL** (does this customer exist?) before touching real tables.
- Production stays clean - if the load fails, the transaction rolls back and production is untouched.
- Debugging: after a run, `stg_*.load_status` shows which rows were LOADED or REJECTED.
- Staging has **no constraints/indexes** so it accepts everything and lets SQL *report* problems instead of crashing
  on the first FK error.

## X. How does your ETL pipeline work?

1. Read job definitions from `etl_jobs` (in FK order) and insert a `RUNNING` row in `etl_execution_logs`.
2. **Extract:** read the CSV with every column as text, so pandas doesn't silently turn "N/A" into NaN.
3. **Schema check:** if a required column is missing → the whole file is rejected, job **FAILED**
   (demo: the bad batch without an `email` column).
4. **Transform:** trim, lower-case emails, title-case names, standardise segment/status codes, normalise phones.
5. **Validate:** required values, email format, valid dates, not in future, numeric/integer, min/max, allowed values,
   duplicates (exact copy = MEDIUM, same key with different data = HIGH). First occurrence is kept.
6. Rejected rows → `data_quality_issues` + a rejected CSV with the reasons.
7. In **one transaction**: load staging → resolve business keys to ids with `UPDATE ... JOIN` → reject rows whose
   reference is NULL → upsert to production → update the execution log (SUCCESS / PARTIAL_SUCCESS).
8. After all jobs: `CALL sp_run_data_quality_checks()` for cross-table rules.

## Y. How do you handle bad data?

- **Never silently drop it:** every rejected row produces an issue with table, record identifier, column, rule,
  type, description (including the CSV row number), severity and status (OPEN → RESOLVED / IGNORED).
- **Fix what is safely fixable** (formatting), **reject what is wrong** (invalid email), and **flag what is
  suspicious but loadable** (Q27 finds the same person registered twice with different emails).
- **Severity** drives priority: CRITICAL (whole file missing a column, overpayment), HIGH (missing value, broken
  reference), MEDIUM (format, exact duplicate), LOW (order dated before signup).
- **Database constraints** as the last line of defence for anything that bypasses the ETL.
- Demo totals: 116 issues - 32 business-rule, 28 invalid references, 14 duplicates, 12 missing values, 10 invalid dates...

## Z. How would you optimize a slow SQL query?

1. **Measure** - find it via the slow query log / `performance_schema`, note the time.
2. **EXPLAIN / EXPLAIN ANALYZE** - look for full table scans, huge row estimates, filesort, temporary tables.
3. **Index** the columns used in WHERE / JOIN / ORDER BY (composite: equality columns first, range last).
4. **Make predicates index-friendly** - `order_date >= '2026-01-01' AND order_date < '2027-01-01'` instead of
   `YEAR(order_date) = 2026` (I showed the plan change from index range scan to table scan).
5. Select only needed columns; paginate with LIMIT.
6. **Pre-aggregate before joining** to avoid fan-out (payments summed per order first).
7. For heavy repeated reports: summary tables / stored derived values (my `order_total`).
8. **Re-measure.**

## 35 likely questions about THIS project (with short answers)

1. **Why did you build this?** - To practise the full data path a company relies on: messy sources → validated,
   constrained database → monitored → served through an API. It covers RDBMS design, SQL and ETL together.
2. **Is the data real?** - No, it's synthetic, generated by my script with a fixed seed, with errors injected on
   purpose (duplicates, bad emails, impossible dates, unknown references) so the validation can be demonstrated.
3. **How many tables, and why that many?** - 12 core tables plus 5 staging tables. I avoided extra tables that add
   nothing - e.g. category is a column, not a table, because it has no attributes of its own.
4. **Why both `customer_id` and `customer_code`?** - The code is the business key from the CRM; the id is a small,
   stable internal key for fast joins. The ETL maps one to the other.
5. **Why is `order_total` stored if it can be calculated?** - Every report needs it; triggers keep it equal to the sum
   of lines, and I verify that with a reconciliation query that returns 0 rows.
6. **What happens if someone inserts an order line by hand?** - The trigger still recalculates the order total; the
   CHECK constraints still reject a quantity of 0 or a discount over 100.
7. **What is a generated column?** - `line_total` is computed by MySQL from quantity, price and discount and stored;
   nobody can write a wrong value into it.
8. **Why DECIMAL for money?** - FLOAT is binary and inexact; DECIMAL stores exact values.
9. **Why CHECK instead of ENUM?** - CHECK is standard SQL, easy to change, and enforced since MySQL 8.0.16.
10. **How do you prevent duplicate payments?** - `payment_reference` is UNIQUE; the ETL flags duplicates in the file;
    the procedure rolls back on a duplicate reference (HTTP 409 in the API).
11. **How do you prevent two people paying the same order at the same time beyond its total?** -
    `SELECT ... FOR UPDATE` locks the order row inside the transaction, so the second payment waits and then sees the
    updated balance.
12. **What did the in-database quality checks find?** - 25 delivered orders not fully paid, 4 overpaid orders,
    2 orders with no lines, 2 payments dated before their order, 2 orders before the customer signed up.
13. **Why were two orders overpaid when you injected only two double charges?** - Four were flagged: two double
    charges, plus two orders whose only line had an unknown SKU, so the line was rejected, the order total became 0,
    but the payment loaded. A good example of how one bad record cascades.
14. **How is the ETL idempotent?** - Upsert on the business key; re-running the same file gave 0 inserts, the same
    totals and no new audit rows (the audit trigger ignores no-change updates).
15. **What's the difference between records_inserted and records_updated?** - Inserted = key was new; updated = key
    already existed and the row was re-applied. Actual value changes show up in the audit log.
16. **What happens if the ETL crashes halfway?** - The load step is one transaction, so it rolls back; the execution
    log is then marked FAILED with the error message. Production never holds half a batch.
17. **Why read CSVs as strings?** - So invalid values are visible to validation instead of being silently converted.
18. **How do you validate in SQL vs Python?** - Python: row-level rules on the file. SQL: rules that need existing data
    (references, email already used by another customer). Constraints: everything else, for every writer.
19. **What was the hardest bug?** - MySQL error 1442: a trigger can't update a table the triggering statement is
    reading. My `INSERT INTO order_items SELECT ... JOIN orders` failed because the trigger updates `orders`. I changed
    the design to resolve ids in staging first, then insert reading only staging.
20. **How does auditing work?** - AFTER triggers on customers, products, orders and payments write table, record id,
    action, old/new JSON, who and when. `changed_by` comes from a session variable the ETL/API set
    (`etl_pipeline`, `api`), falling back to the MySQL user.
21. **Can someone edit the audit log?** - No - BEFORE UPDATE/DELETE triggers on `audit_logs` raise an error.
    (A DBA with DROP rights could still remove it; in production you'd also restrict privileges.)
22. **Why doesn't audit_logs have a foreign key?** - It stores rows from four tables and must survive deletions;
    a FK would prevent both.
23. **Why not log changes from the application instead of triggers?** - Triggers catch changes from *any* client:
    ETL, API, or someone using the MySQL console.
24. **How does the API call stored procedures?** - SQLAlchemy `text("CALL sp_update_order_status(:id, :status)")`
    with bound parameters; errors raised by `SIGNAL` are mapped to HTTP 400 in one helper.
25. **How do you prevent SQL injection?** - All queries use bound parameters or the ORM; user input is never
    concatenated into SQL. Pydantic validates types and allowed values before the DB is reached.
26. **Why FastAPI?** - Fast to build, type hints + Pydantic validation, automatic Swagger docs at `/docs`.
27. **Why SQLAlchemy and raw SQL together?** - ORM for simple filtered lists; raw SQL for analytics where window
    functions and views are clearer as SQL.
28. **How is pagination done?** - LIMIT/OFFSET plus a COUNT of the same filtered query; page_size capped at 100.
    For very large tables I would switch to keyset pagination (`WHERE id < last_seen_id`).
29. **How does the frontend talk to the backend?** - Axios calls `/api/...`; in development Vite proxies to FastAPI;
    CORS is configured for separate deployments.
30. **What is a view and where did you use one?** - A saved query. `vw_order_summary` gives payment status and balance
    per order; `vw_etl_job_status` uses ROW_NUMBER to show each job's latest run; the API maps views to read-only models.
31. **What does EXPLAIN tell you?** - Access type (table scan vs index range/lookup), which index, estimated rows,
    extra steps like sorting. `EXPLAIN ANALYZE` adds real times and row counts.
32. **When would an index not be used?** - Function on the column, leading wildcard `LIKE '%x'`, low selectivity,
    a composite index whose first column isn't filtered, or when the optimizer estimates a scan is cheaper.
33. **How did you test it?** - 43 pytest tests: constraints (CHECK/FK/UNIQUE error codes), triggers, functions vs views,
    procedures incl. rollback of overpayment and duplicate reference, every API endpoint and filter, and ETL rules.
    Plus manual EXPLAIN checks and clicking through the dashboard.
34. **How would you scale this?** - Batch/chunked loading for big files, partitioning `orders` by date, read replicas
    for reporting, a scheduler (cron/Airflow) for the ETL, caching dashboard KPIs, and a proper warehouse
    (star schema) for heavy analytics.
35. **What would you improve next?** - Authentication and roles, a scheduler for the ETL, CDC/incremental loads by
    timestamp, data-quality thresholds that fail a job, and Docker Compose for one-command setup.

## Demo script for the interview (5 minutes)

1. Dashboard: "204 customers, 1,525 orders, ₹23.86 Cr revenue, 1 failed ETL run, 116 open issues."
2. ETL Monitoring: show the PARTIAL_SUCCESS runs, the SUCCESS delta run, and the FAILED run's error "Missing columns: email".
3. Data Quality: filter CRITICAL → overpayments and missing column; open an INVALID_REFERENCE issue.
4. Orders: open a delivered order, try to set it back to PENDING → "Invalid status transition" (from the procedure).
5. Audit Log: filter UPDATE → show old → new values written by triggers.
6. Terminal: run Q21 or Q22, then `EXPLAIN` example 2 vs 1.
